# MAKE UP 会员与积分支付合同

更新日期：2026-09-18

## 现役模型

正式商业主路径是唯一的 MAKE UP Pro（高频会员）：“月度会员 + 每月积分”。Stripe 使用真正的 recurring subscription；ZPAY 使用每月重新支付的人工续费订单。一次性积分包只保留历史订单兼容，不再向新用户公开销售。

### 账期与权益

- 服务端目录提供单次报告、月卡和年卡；客户端不自行决定价格或权益。
- 单次报告 ¥19.9 / US$2.99 发 100 积分；月卡 ¥59 / US$8.99 发 1000 积分并每天刷新 50 次普通匹配；年卡 ¥599 / US$89.99，连续 12 个月每月发 2000 积分并不限普通匹配。
- 完整报告消耗 100 积分，并包含公开博主名字线索；原 3 积分独立推荐已经退役。
- 积分永久有效；取消续费后本期继续有效，Stripe 在账期结束时取消；支付失败不发新积分。
- 每个账号只能有一个开放订阅；重复 webhook、重复 invoice 或重复 ZPAY 回调都不得重复发分。
- 新会员不创建或续期旧 Plus，也不获得不限次普通匹配。

## 数据表

- `membership_plans`：服务端价格、币种、每月积分和 Stripe Price 配置。
- `subscriptions`：账号、供应商、档位、当前账期、取消续费状态和供应商订阅 ID。
- `subscription_cycles`：每个已确认账期一行，唯一约束负责幂等发分。
- `payment_orders`：保留一次性订单和会员首期 / ZPAY 月续费订单的最小状态。
- `reward_wallets` + `entitlement_ledger`：余额与不可变积分流水。

禁止在上述表中写入照片、面部比例、博主名称、AI 输出、卡数据、原始供应商回调或支付凭证。

## Provider 行为

### Stripe

1. 创建 Checkout `mode=subscription`，使用服务端 recurring Price 或测试阶段的 `price_data.recurring.interval=month`。
2. 在 Checkout 和订阅 metadata 中写内部订单 ID、档位和产品类型，不写用户内容。
3. 只把 `invoice.paid` 当作账期发分依据。
4. 处理 `customer.subscription.created/updated/deleted`、`invoice.paid`、`invoice.payment_failed` 和 `invoice.payment_action_required`。
5. 取消续费只设置 `cancel_at_period_end`，不得立即收回当期积分。

### ZPAY

1. 创建“本月会员”跳转订单，回调仍使用现有签名校验。
2. 回调调用 `fulfill_manual_membership_payment`，激活或延长一个月并发放一次账期积分。
3. 不假设 ZPAY 自动扣款；只有官方文档明确提供周期扣款协议并完成测试后才新增。

## 失败、退款与幂等

- 支付未确认、Checkout 过期或失败：不发积分。
- 账期重复事件：`subscription_cycles` 唯一键 + `entitlement_ledger.idempotency_key` 双重阻止重复发分。
- 会员退款：首期退款和订阅取消是两个动作；退款前必须按供应商规则检查已消费积分，不能造成负余额。
- 报告失败：沿用现有预占、消费、退回函数，不与会员账期混用。旧 AI 推荐流水只做历史兼容。

## 前端合同

`/subscription` 独立展示单次报告、月卡、年卡及两种币种；`/report` 只承载报告生成，旧 `/plus` 链接兼容跳转到 `/report`。支付开关关闭时只展示方案，不创建订单。历史积分包不提供购买入口。

## 管理台与复核

订单、订阅、账期发分、消费、退回和退款分开聚合。每周复核：会员页访问、Checkout 开始、首期支付、账期发分、7 天内积分使用、报告保存、退款和失败。主动反馈只用于定位负向案例，不作为整体符合率。

## 上线安全门

1. 数据库迁移和 RLS。
2. Stripe 账期、重复 invoice、取消续费、支付失败的技术验收。
3. ZPAY 小额支付、重复回调、回跳查询、人工退款。
4. 老积分余额 / 旧订单兼容。
5. 生产前端保持支付关闭；所有技术证据通过后再打开入口。本阶段不再做价格或套餐 A/B 测试。
