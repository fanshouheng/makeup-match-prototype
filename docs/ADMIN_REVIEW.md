# 博主入库审核 SOP

本文件供项目运营人员使用，不是用户说明。审核在 Supabase Dashboard 中完成，不需要把 secret key 放进浏览器或本地前端。

## 1. 查看待审申请

打开生产站点 `/admin`，输入已授权管理员邮箱并发送登录链接。打开邮件中的链接后进入管理台；不同设备可以分别保持登录，退出时只退出当前设备。服务端仍按 `ADMIN_USER_IDS` 中的不可变 Auth UUID 授权，不按邮箱字符串授权。

```sql
select
  id,
  name,
  contact_email,
  platform,
  profile_url,
  tutorial_url,
  reference_audience,
  content_types,
  reference_photo_path,
  submitted_at
from public.creator_submissions
where status = 'pending'
order by submitted_at asc;
```

不要把联系邮箱、未审核照片或完整申请表复制到公开文档、聊天群或问题追踪系统。

AI 联网推荐和完整妆造报告返回的名字都不是入库申请，也不代表主页归属、合作或照片授权已经核验。不得仅依据 AI 名字下载博主照片、提取面部特征、批准入库或写入博主跟进台账；需要入库时仍应由博主本人或授权代表提交并完成本 SOP 的核验。

## 2. 核验主页归属

至少完成以下一项：

1. 使用申请邮箱联系申请人，请对方从所选平台主页的公开联系方式回复。
2. 请申请人在主页简介中临时放置一次性核验文字，核验后删除。
3. 已经建立直接联系时，通过对应平台账号私信确认申请编号。

同时检查：

- 申请名称与主页主体一致。
- 正脸照属于申请人本人，并明确同意用于公开匹配。
- 照片清晰、单人、正面，不含其他人的个人信息。
- 参考页面与申请人的公开内容一致。
- 形象参考、发型或妆容等内容方向与代表内容一致。
- 代表内容来自申请主页或获得了明确授权。

核验通过后记录时间：

```sql
update public.creator_submissions
set ownership_verified_at = now()
where id = '申请 UUID'
  and status = 'pending';
```

## 3. 批准入库

```sql
select public.approve_creator_submission('申请 UUID');
```

批准后检查公开创作者库：名称、授权照片、主页、参考页面、内容方向和代表内容链接应正确显示，联系邮箱不应出现。

## 4. 拒绝申请

```sql
update public.creator_submissions
set
  status = 'rejected',
  reviewed_at = now(),
  review_note = '简短、客观的拒绝原因'
where id = '申请 UUID'
  and status = 'pending';
```

随后在 Supabase Storage 的 `creator-photos` 桶中删除该申请的 `reference_photo_path`。不要直接删除 `storage.objects` 表记录；应使用 Storage Dashboard 或 Storage API，确保底层文件同时删除。

确认照片删除后，可以删除不再需要保留的拒绝申请：

```sql
delete from public.creator_submissions
where id = '申请 UUID'
  and status = 'rejected';
```

## 5. 撤回、下架与删除

收到申请人请求后，先通过原联系邮箱或主页归属重新核验身份。

立即停止公开展示：

```sql
update public.creators
set is_active = false, updated_at = now()
where submission_id = '申请 UUID';
```

确认页面不再展示后：

1. 在 Storage Dashboard 删除对应授权照片。
2. 删除公开记录。
3. 删除原申请记录。

```sql
delete from public.creators
where submission_id = '申请 UUID';

delete from public.creator_submissions
where id = '申请 UUID';
```

## 6. 查看产品数据

打开生产站点的 `/admin`，使用 UUID 已加入 `ADMIN_USER_IDS` 的已确认管理员账号登录，再切换到“产品数据”页签。页面默认显示按北京时间计算的最近 7 个自然日，也可以选择开始和结束日期后查询指定日期范围；开始日和结束日都会计入。页面展示以下匿名标签页会话指标：

- 有效访问：至少进入过一次公开产品的会话数。
- 选择照片率：`选择照片会话 / 有效访问会话`。
- 女生模式选图会话：在女生模式选择过照片的会话数，以及占全部选图会话的比例。
- 男生模式选图会话：在男生模式选择过照片的会话数，以及占全部选图会话的比例。
- 分析完成率：`分析成功会话 / 选择照片会话`。
- 失败原因：未检测到人脸、多张人脸、照片过暗、角度或画面问题、分析组件异常；旧页面产生的失败会单独显示为未分类。
- 结果到达率：`结果展示会话 / 分析成功会话`。
- 反馈率：`提交符合或不符合的会话 / 结果展示会话`。
- 主动反馈覆盖：`（符合反馈 + 不符合反馈）/ 结果展示`。这只是反馈参与率；反馈者存在选择偏差，不能外推整体匹配质量。
- 不符合原因：有效负反馈数，以及分析不对、博主不像、风格不适合、没解决化妆问题、其他五类多选原因的次数与占比。
- 博主点击率：`点击过任一创作者主页或代表内容的会话 / 结果展示会话`。
- 分享率：`首次成功分享会话 / 结果展示会话`。
- Plus 历史意向数据：查看切换前按 9.9 元、19.9 元、29.9 元记录的曝光、展开、配置完成、愿意购买、价格偏高和暂不需要；这些数据只作历史归档，不再发送新事件，也不代表积分订单。

同一会话的同一事件只计一次；同时体验女生和男生模式时会分别计入两项，因此两项比例之和可能超过 100%。失败原因只保存固定代码，不保存原始异常。结构化负反馈只保存随机标签页会话 UUID、当次展示过的博主 UUID 无顺序集合、固定算法版本、原因代码、可选的最多 160 字“其他”原因和服务端时间；不保存照片、面部比例、匹配分数、设备身份、博主名称、具体链接、推荐名次或邮箱。指标从对应记录功能上线后开始累计，没有历史补录。

有效负反馈未满 50 条时只继续收集，不提前调整产品。达到 50 条后按选择次数最多的固定原因判断：分析不对最多时先修面部分析；博主不像最多时检查博主覆盖和排序；风格不适合最多时在匹配前增加风格偏好；没解决问题最多时转向具体化妆方案。最高原因并列时继续收集，不强行下结论；“其他”最多时先人工复核短文本。
历史实验中，Plus 三种意向反馈合计每个会话最多记录一次；原判断阈值只用于解释切换前数据，不再控制当前固定价邀请制内测。历史 Plus 统计不包含场景、妆造方向、联系方式或支付资料。

切换到“AI 调用”页签，可以查看产品数据页选择范围内实际发送到第三方 AI 服务的调用总数、成功率、最近记录平均耗时、固定语言/市场/平台分布和最多 50 条调用记录。每条记录只包含调用时间、成功或失败、耗时、固定错误分类、上游 HTTP 状态和参考模式；不包含照片、面部比例、提示词、AI 返回名字、推荐结果或原始 IP。安全验证失败、限流和无效图片没有调用 AI，因此不会进入该列表。

需要在 Supabase SQL Editor 复核原始事件数量时，可以运行：

```sql
select event_name, failure_reason, count(*) as sessions
from public.product_events
where created_at >= now() - interval '7 days'
group by event_name, failure_reason
order by event_name, failure_reason;

select reason_code, count(*) as selections
from public.match_negative_feedback,
unnest(reason_codes) as reason_code
where created_at >= now() - interval '7 days'
group by reason_code
order by selections desc, reason_code;
```

## 7. 日常维护

每周检查：

- 是否存在超过 7 天未处理的待审申请。
- 是否存在数据库写入失败后留下的孤立照片。
- 是否有失效的抖音、小红书主页或代表内容链接。
- Edge Function 是否出现大量 `captcha_failed`、`rate_limited`、`provider_request_failed` 或上传失败日志。

限流表只保存加盐哈希，可以清理超过 24 小时的窗口：

```sql
delete from public.creator_submission_rate_limits
where window_started_at < now() - interval '24 hours';

delete from public.ai_creator_discovery_rate_limits
where window_started_at < now() - interval '24 hours';

delete from public.ai_creator_discovery_logs
where created_at < now() - interval '30 days';
```

历史 AI 限流表只保存加盐单向哈希和计数窗口；独立 AI 推荐退役后不再产生新调用。男生报告不会写入旧 AI 推荐调用日志；不要把照片、面部比例、提示词、生成报告、AI 返回名字或推荐结果加入日志、审核记录、产品事件或运营台账。

产品事件只用于短期产品验证。需要延长统计周期或导出数据前，先复核隐私说明和最小化原则，不要加入会话以外的用户标识或任何匹配内容。

审核记录只写完成判断所需的信息，不额外收集身份证、手机号、住址等资料。

## 8. 记录博主跟进

打开生产站点的 `/admin`，登录后切换到“博主跟进”。每联系一位博主新增一条记录，系统会自动生成 `B001` 形式的候选编号。

只记录完成跟进所需的信息：博主称呼、公开主页、首次联系日期、当前阶段、下次跟进日期、流失原因和简短备注。不要保存聊天截图、私人手机号、身份证或住址。状态变为“已拒绝”或“未回复”时必须填写原因；下次跟进日期不能早于首次联系日期。

该台账是管理端私有数据。`creator_outreach` 不向 `anon` 或 `authenticated` 开放，浏览器只能通过 JWT 保护的 `admin-review` Edge Function 访问。定时验证报告只统计各阶段人数和逾期待跟进数，不得写入姓名、主页链接或备注。

## 9. 处理旧 Plus 邀请码

该工具仅用于处理积分制上线前已经承诺的旧 Plus 邀请。正式目录包含单次报告、月卡与年卡；管理台人工开通只处理月卡（1000 积分、每日 50 次普通匹配），年卡通过支付目录购买。历史积分包只做兼容，新会员不创建或续期旧 Plus。

- 每笔已确认付款只签发一个邀请码。
- 邀请码明文只显示一次，应立即发送给对应用户，不要粘贴到公开文档或工单。
- 邀请码 30 天内有效，只能激活一个已确认邮箱的账号；已经兑换的旧码不能用于续期。
- 不要在邀请码表、管理台备注或日志中保存微信聊天、付款账号、付款凭证、照片、面部比例、报告或匹配结果。
- 用户称邀请码无效时，先核对是否输入完整、是否过期以及登录邮箱是否正确；不要直接签发多个备用码。

## 10. 人工发放积分

用户先注册账号并完成邮箱确认。需要人工补发或线下确认时，打开 `/admin` 的“Plus 邀请”页签，在“发放积分”中填写账号邮箱和正整数积分。

- 每个补发原因只操作一次；页面成功后会显示该账号当前积分余额。
- 不得借此单独发放或出售普通匹配次数。完整报告每次 100 积分；不再提供 3 积分独立 AI 推荐。
- 不要在权益表、备注、日志或工单保存微信聊天、付款账号、付款凭证、照片、面部比例、匹配结果或 AI 返回名字。
- 邮箱不存在时，先让用户完成普通账号注册和邮箱确认，不要代用户创建密码。

## 11. 线上订单全额退款

先在 Stripe 或支付宝支付服务后台核对订单、退款条件和应退金额，再打开 `/admin` 的“产品数据”，展开“退款处理”。从供应商订单元数据取得 MAKE UP 内部订单 UUID，输入后再键入 `REFUND`。

- 只处理状态为 `paid` 的 Stripe/支付宝线上订单，并按原订单金额全额退款；不支持部分退款。
- Stripe/支付宝支付服务明确返回成功后，系统才把订单改为 `refunded` 并回滚本次订单增加的权益；Stripe 的全额退款 webhook 也会执行相同的幂等事务。
- 相同订单重复提交退款或供应商重复发送通知，不会重复扣减权益。
- 订单发放的积分已有部分被使用时，管理台阻止自动全额退款，转人工判断；不得让积分余额变为负数。
- 人工收款订单仍在线下退款，不要使用此工具伪造供应商成功状态。
- 管理台不展示供应商订单号、回调原文或付款凭证；不要把这些内容写入备注、文档或日志。

## 12. 查看注册、支付与会员情况

打开 `/admin` 后默认进入“用户与订单”。页面只展示日常运营需要的受保护数据：注册总数、邮箱确认情况、近 30 天注册、最近 100 个账号、订单状态与金额、当前会员状态和到期时间。

- 账号邮箱只在管理员鉴权通过后返回，不得导出、公开或用于未获同意的营销触达。
- 订单列表不展示供应商回调原文、签名、付款账号、卡信息或付款凭证。
- 会员名单只取每个账号最近一条订阅状态；历史订单仍在订单列表中单独核对。
- 点击“增加会员”进入人工会员管理。用户必须先自行注册并完成邮箱确认，管理员不代建密码。
- 页面显示“数据接口尚未部署”时，先部署 `20260918110000_admin_commerce_overview.sql` 和最新版 `admin-review`，不要用公开查询替代管理员接口。

## 13. 手动管理会员与套餐

打开 `/admin` 的“会员与套餐”页签。按已确认邮箱查询账号后，可以人工开通或延长一个月，也可以立即停止非 Stripe 会员。

- 每次“开通 / 延长 1 个月”按当前 MAKE UP Pro 套餐发放一个账期积分；重复请求由幂等键阻止重复发分。
- 停止会员不会回收已经发放的积分。Stripe 自动订阅必须先在 Stripe 后台取消，管理台不会直接覆盖供应商状态。
- 套餐设置同时维护支付宝人民币月费、Stripe 美元月费、每月积分和目录开放状态；历史三档保持停用。
- 关闭套餐目录只阻止新支付，不会取消现有订阅。
- 审计表只保存管理员 ID、用户 ID、订阅 ID、动作、发放积分和时间，不保存付款凭证、聊天、照片、面部数据或 AI 内容。
